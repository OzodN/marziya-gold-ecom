# Правила и регламенты для AI-агентов (Root AGENTS.md)

Данный документ является главным сводом правил для всех AI-агентов, работающих в репозитории `marziya-gold_ecom`. Он автоматически обнаруживается и загружается средой Antigravity.

---

## 1. Иерархия источников истины (Source of Truth Hierarchy)
1. **Продуктовые требования:** `docs/architecture/product-architecture.md` (лаконично — в `.ai/context/`).
2. **Архитектурные решения:** `docs/adr/*.md`.
3. **Контракт API:** `docs/api/openapi.yaml` (единственный канонический контракт между Backend и Frontend).
4. **Схема базы данных:** `apps/backend/src/main/resources/db/migration/*.sql` (Flyway-миграции).
5. **Состояние задач:** `.ai/work/registry.yaml` и `task.yaml`.
6. **Сгенерированное состояние (`.ai/state/generated/`):** **НЕ ЯВЛЯЕТСЯ ИСТОЧНИКОМ ИСТИНЫ**.

Подробный регламент: `.ai/instructions/source-of-truth.md`.

---

## 2. Обязательный порядок загрузки контекста (Context Loading)
Перед выполнением любой задачи агент обязан:
1. Прочитать настоящий корневой `AGENTS.md` и локальный `AGENTS.md` своей рабочей директории.
2. Прочитать `.ai/context/project.md`, `.ai/context/terminology.md`, `.ai/context/constraints.md`, `.ai/context/non-goals.md`.
3. Загрузить спецификацию назначенной задачи из `.ai/work/tasks/<TASK-ID>/task.yaml` и `plan.md`.
4. Активировать назначенные навыки из `.ai/stack/aas-stack.json` через глобальный каталог `~/.gemini/antigravity-cli/skills`.
5. **ЗАПРЕЩЕНО** читать весь монолитный контекст или исходники чужих директорий без явной необходимости.

Подробный регламент: `.ai/instructions/context-loading.md`.

---

## 3. Принципы владения кодом (Code Ownership)
- Каждый агент имеет строго очерченную зону владения (см. `.ai/orchestration/ownership.yaml`).
- **СТРОГО ЗАПРЕЩЕНО** модифицировать файлы в чужой директории без координации и прохождения соответствующего шлюза (`.ai/orchestration/gates.yaml`).
- Агент `frontend` никогда не правит код в `apps/backend/` или `database/`.
- Агент `backend` никогда не правит код в `apps/frontend/` или `.github/`.
- Общие контракты (`docs/api/openapi.yaml`) правятся только по регламенту `.ai/workflows/architecture-change.md`.

---

## 4. Правила параллельной разработки и Git (Parallel Development & Git)
1. **Изоляция рабочих пространств:** Никакие два агента не работают в одной рабочей директории одновременно.
2. **Использование Git Worktrees:** Каждая задача выполняется в отдельном ворктри по протоколу навыка `using-git-worktrees`:
   ```bash
   git worktree add .worktrees/<TASK-ID>-<slug> -b feat/<TASK-ID>-<slug>
   ```
3. Все ворктри создаются строго внутри скрытой папки `.worktrees/` (проверено в `.gitignore`).
4. **Соглашение о коммитах:** Строго Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`).
5. Основная ветка `main` защищена. Изменения интегрируются только через PR/ревью Оркестратором.
6. Агенты никогда не перезаписывают чужие незакоммиченные изменения.

---

## 5. Управление задачами и жизненный цикл (Task State)
- Все задачи регистрируются в `.ai/work/registry.yaml`.
- Разрешенные состояния: `draft`, `ready`, `in_progress`, `blocked`, `review`, `qa`, `done`, `cancelled`.
- Агент начинает работу только тогда, когда задача находится в статусе `ready`.
- Зависимости между задачами строго соблюдаются (задача `blocked` не берется в работу, пока зависимость не станет `done`).

---

## 6. Протокол передачи задач (Handoffs)
- По завершении работы в ворктри агент обязан составить дюрабельный отчет `.ai/work/tasks/<TASK-ID>/handoff.md`.
- Хендофф содержит: выполненную работу, список измененных файлов, принятые решения, допущения, выявленные проблемы, результаты валидации и следующие шаги.
- Передача задач "на словах" запрещена.
- Шаблон хендоффа: `.ai/work/handoffs/template.md`.

---

## 7. Требования к тестированию (Testing Expectations)
- Любой новый код должен сопровождаться тестами.
- Backend: юнит-тесты сервисов и срез-тесты контроллеров (JUnit 5, Mockito).
- Frontend: компонентные тесты и E2E сценарии критических путей (Playwright).
- Перед оформлением хендоффа агент обязан лично выполнить команду тестирования и убедиться в отсутствии падений.

---

## 8. Требования к безопасности (Security Expectations)
- **Zero-Trust к клиенту:** все данные, приходящие из подборки или формы, валидируются на бэкенде.
- **Хранение токенов:** JWT авторизации мастера хранится исключительно в `HttpOnly`, `SameSite=Strict`, `Secure` Cookie.
- **Никаких секретов в Git:** пароли БД, ключи Cloudinary и JWT-секреты передаются только через переменные окружения.
- **Rate Limiting:** публичные эндпоинты защищаются ограничителем запросов (Bucket4j).

---

## 9. Критерии готовности (Definition of Done)
Задача считается `done` только при выполнении следующих условий:
1. Все приемочные критерии из `task.yaml` удовлетворены.
2. Код не нарушает границ владения (`ownership.yaml`).
3. Локальные тесты и линтеры завершились без ошибок.
4. Создан и заполнен `handoff.md`.
5. Получено подтверждение от `reviewer` (шлюз `code_review_gate`), а для фронтенд-задач — также от `ux-reviewer` (шлюз `ux_review_gate`).
6. Ворктри удален, ветка влита в `main`, статус в `registry.yaml` обновлен на `done`.
